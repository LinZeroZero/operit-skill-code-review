# 注释：审查判据

对应 §2.4 的 Comments 维度，以及 §2.7 的「注释与被注释对象」触发项。
本文件只回答两件事：**什么算问题、什么不算问题**。不讨论注释怎么写好看——那属于风格，§7 明确不做。

## 1. 腐烂（判 🟡；若注释直接导致错误用法，升 🔴）

**先确认哪一方错**：注释与代码不一致，只说明**有一方**错，不说明是哪一方。先按阶段 1 的「代码要做什么」（commit message / PR 说明 / 测试）确认意图——

- 代码偏离意图 → 按**功能 bug** 报，不要报成注释腐烂；
- 注释偏离意图 → 才按本节报腐烂。

例：注释写「最多重试 3 次（限流阈值）」，PR 说明写「阈值不变，只调大 sleep」，代码却改成 5 次。真实失效是**代码 bug**；若以代码为准直接比，会产出一条「注释腐烂（旧 3 / 现 5）」的错误 finding，把真 bug 记成文档问题。

升 🔴 必须附一条**误用路径**：谁照着这条注释做、会得到什么错误结果。写不出这条路径就留在 🟡 —— 用未验证的因果把严重度调高，和 §3 里「依据写不出就降级存疑」是同一个要求。

**判据**：本次改动改变了下面任一项，而描述它的注释未同步。

- 函数签名（参数增减、顺序、默认值）
- 返回值含义（单位、是否含缓存、空值语义）
- 抛出的异常 / 错误码
- 行为分支（条件改了、阈值改了、执行顺序改了）
- 注释里的示例 / 命令 / 配置片段（`foo(a, b)` 而签名已三参、贴的 `adb` 输出与当前不符）—— 读者复制即失败，属「直接导致错误用法」，可直判 🔴

**位置写法**：`file:line` 指向注释所在行。

七列表里这样填：「问题」列写**旧行为**（注释现在说的还是什么），「依据」列写**现在是什么**（当前代码里能指认的证据：签名行 / 返回值类型 / 分支条件）。
只写「注释过时」不算 finding：旧的和现在的都必须能指认，缺一项就降级到「存疑」。

**为什么单列这一项**：它是本文件里唯一有量化证据的判据。

- Radmanesh, Imani, Ahmed, Moshirpour. *Investigating the Impact of Code Comment Inconsistency on Bug Introducing*. arXiv:2409.10781v1 [cs.SE], 2024-09-16。
  结论：代码改了而注释未跟上的提交，**引入 bug 的概率约为一致改动的 1.5 倍**；影响在注释刚失效时最大，随时间衰减。
- Tan, Yuan, Krishna, Zhou. `/* iComment: Bugs or Bad Comments? */`. SOSP 2007（21st ACM SIGOPS Symposium on Operating Systems Principles）。
  首次系统论证：注释与代码不一致在实践中普遍存在，且会误导后续维护者。

**既有腐烂照报**：注释早已在描述旧行为、而本次改动没碰它，照样出 finding —— 在「问题」列开头标「非本次引入」，与 §9「分开写『原文本来就是错的』和『我这轮改错的』」同一口径。

**注意**：这条要求「改动与注释在同一视野内」。跨文件的情况（改了 A 的返回值，B 的注释在描述它）两端都要指到，只写一端不算结论。

## 2. 复述（判 Nit，不判 blocking）

**判据**：删掉这条注释，信息量为零——它只是把紧邻的代码用自然语言重说一遍。

| 算 | 不算 |
|---|---|
| `i++; // i 加 1` | `// 重试 3 次：厂商侧首次 bind 常失败` |
| `x = null; // 设为 null` | `// 这里必须 sleep 200ms，否则 wm size 返回旧值` |
| `// 遍历数组` 后接 for 循环 | `// 故意不复用上面的连接：两条流会互收对方的回复` |

分界线是「**是否包含代码里读不出来的信息**」。理由、外部系统怪癖、被否掉的方案、魔数来源，都算信息；「做了什么」不算。

## 3. 不算问题（守住 §7 边界）

以下几类**不得**写成 finding：

- **注释语言**（中/英）、**行长**、`//` 与 `/* */` 的选择 —— 交 linter 与项目约定，属 §7「不评格式」。
- **注释密度**。业内没有公认标准，任何「注释太少」的判定都是口味；注释多有时反而是坏信号（代码表达不清才会依赖注释）。
- **缺注释本身**。只有「代码无法自解释、且缺失会导致具体误用」时才提，并且必须写出那个后果；写不出后果就不是 finding。

## 4. 只记一行 nit 的

以下按 Clean Code 第 4 章的分类属于坏注释。**仍按 §3 的七列记一行，只是每列很短**：问题列写它属于哪类，依据列写为什么多余（`git log` 已有 / 与紧邻代码重复），建议列写「删」，存疑列写 `—`；改动没碰过就不提。

与 §3 的 🟡「会误导后来人」的分界：🟡 留给**陈述了错误事实**的注释（读者会照着做错）；这里三类是**多余但不误导**（不会被带错方向，只多花读的时间）：

- 修改历史、作者、日期 —— `git log` / `git blame` 是唯一真相源
- 注释掉的代码 —— 版本控制已保存，留着只增加读的成本
- 分节横幅（`####`、`----`）—— 通常说明函数太长，该拆函数

## 5. 能机械化的别靠眼

**已确认能查一致性的：darglint 与 C# 编译器这一级**；其余三个查的是语法与链接，跑绿了不代表注释与代码一致：

| 语言 | 工具 | 查什么 |
|---|---|---|
| Python | `ruff` 的 D 规则（pydocstyle） | docstring 缺失、格式 |
| Python | `darglint` | `@param` / `@return` 与真实签名不一致 |
| TypeScript | `eslint-plugin-tsdoc` | TSDoc 标签语法错误 |
| Rust | `rustdoc::broken_intra_doc_links` | 文档内链接断链 |
| C# | Roslyn `CS1572` / `CS1573`（需开 `DocumentationFile`） | `<param>` 标签缺失，或与签名对不上 |

本表不穷举：只列已确认过的检查器。探测不到对应语言的工具就写明「靠人工」，不要写成「无工具可用」。

**先探测再跑**：`command -v darglint` 或对应语言的检查器，没装就回到人看，并在报告里写明「该工具未安装，本节靠人工」。把没跑过的工具当成已核对，是本文件最想防的那类假证据。

**没有工具能查的**：注释是否复述代码、是否写了「为什么」。这两件是语义判断，只能人看——这也是本文件要写判据的原因。能跑工具的场合，说「跑过」并贴输出；不要把「我看了一遍觉得没问题」写成验证。

## 6. 一条限制（自查用）

「腐烂」这一项**不能靠读 diff 单独完成**：diff 只显示改动行，而失踪的注释往往在改动行之外。

必查步骤：拿到改动涉及的函数/类名 → 去它定义处读一眼注释现状。

只读 diff 就报「注释无问题」，与 §2.6 的「低频采样得到假阴性」同类：证据的覆盖范围小于断言的覆盖范围。

除人工去定义处看，再按标识符机械扫一遍：把本次改动涉及的函数名 / 参数名 / 字段名逐个 `grep -rn '<名字>'` 全仓，筛出含注释符的行，逐条判是否还在描述旧行为。这一步补的是「不知道还有哪些文件的注释提过它」——跨文件腐烂靠翻页必漏。

适用边界（写清是为了不让它变成新的假证据）：
- 改动没有可搜的标识符（删了一个分支、改了阈值）→ 这条不管用，仍要人工读 diff 上下文；
- 注释用自然语言指代、没写标识符（「返回值保证非空」而没写函数名）→ 命中不到；
- 名字过于通用（`size` / `get` / `run`）→ 噪音大于信号，改为只搜限定名（`类.方法`）。

**怎样算够**：把改动的 N 个标识符逐个 `grep`，报告里写清「搜了哪几个名字、命中几个文件、逐条判读结论」；没有命中也要写「grep 不到」——否则「注释无问题」是一句没有证据的话。
